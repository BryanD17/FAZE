1.6 MYSQL MIGRATION WORKFLOW (VIA CLI — REQUIRED)
--------------------------------------------------------------------------------

There is no Supabase and no ORM auto-sync in this project. Schema changes are
plain SQL files applied by a small CLI runner you build in AGENT 01.

    db/
      migrations/
        0001_init_core_tables.sql
        0002_add_group_membership.sql
        ...
      seeds/
      scripts/
        migrate.js        # applies pending migrations in order
        rollback.js       # applies the paired .down.sql
        reset.js          # drop + recreate + migrate + seed (dev only)

Rules:
  - Sequential 4-digit prefix. Never reuse a number. Never reorder.
  - Every migration is idempotent: CREATE TABLE IF NOT EXISTS,
    DROP ... IF EXISTS, CREATE OR REPLACE VIEW, guarded ALTERs.
  - Every migration has a matching `NNNN_*.down.sql`.
  - Applied migrations are recorded in a `schema_migrations` table
    (filename, checksum, applied_at). The runner refuses to re-apply and
    refuses to run if a previously-applied file's checksum changed.
  - Apply with:  `npm run db:migrate`
  - Verify with: `npm run db:status` (prints applied vs pending)
  - Record the CLI output verbatim as evidence in APPENDIX A.

Local MySQL, via CLI:
    mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS faze
      CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
    mysql -u root -p faze -e "SHOW TABLES;"
    mysqldump -u root -p faze > db/dumps/faze_$(date +%Y%m%d).sql

Docker alternative (preferred so all four teammates match):
    docker compose up -d db
    docker compose exec db mysql -uroot -proot faze -e "SHOW TABLES;"

1.7 EXTERNAL DATA WORKFLOW (KAGGLE SEED + API ENRICHMENT — VIA CLI)
--------------------------------------------------------------------------------

FAZE uses a two-source data strategy. Both are real. Neither is invented.

  A) KAGGLE (bulk seed — the game catalog)
     Install and authenticate:
         pip install kaggle
         # Kaggle account → Settings → API → "Create New Token"
         # save kaggle.json to ~/.kaggle/kaggle.json && chmod 600 it
     Download into db/data/raw/ (never commit raw dumps; .gitignore them):
         kaggle datasets download -d fronkongames/steam-games-dataset -p db/data/raw --unzip
         kaggle datasets download -d antonkozyriev/game-recommendations-on-steam -p db/data/raw --unzip
     Fallbacks if a slug 404s (dataset slugs rot — search, don't guess):
         kaggle datasets list -s "steam games"
         kaggle datasets list -s "video game ratings"
     If Bryan has no Kaggle token yet, mark ⛔ BLOCKED with: "Bryan: create a
     Kaggle API token at kaggle.com/settings and save it to ~/.kaggle/kaggle.json"
     — and in the meantime proceed using the API path (B) so the build is not
     stalled.

  B) LIVE APIS (enrichment — cover art, genres, platforms, popularity)
     - RAWG  : https://api.rawg.io/api/games  (free key, generous limits)
     - IGDB  : https://api.igdb.com/v4/games  (Twitch client id + secret)
     - Steam : https://api.steampowered.com/ISteamApps/GetAppList/v2/ (no key)
     Keys live in server/.env as RAWG_API_KEY, IGDB_CLIENT_ID,
     IGDB_CLIENT_SECRET. Document each in .env.example. If a key is missing,
     the ETL must skip enrichment with a clear log line, not crash, and the
     agent records ⛔ BLOCKED naming the exact key.

  ETL rules (enforced in AGENT 02):
     - Raw → staging tables (`stg_*`, loose types) → validated → normalized
       core tables. Never load a CSV straight into a production table.
     - Idempotent upserts keyed on a natural key (steam_appid / rawg_id /
       igdb_id), never on an auto-increment.
     - Every ETL run writes a row to `etl_runs` (source, rows_in, rows_loaded,
       rows_rejected, started_at, finished_at, status).
     - Rejected rows go to `etl_rejects` with a reason. Silent drops are a bug.
     - Rate limits respected with backoff. Cache API responses to
       db/data/cache/ so re-runs are free.

4.1 THE TECH STACK (decided — do not substitute without updating this doc)
--------------------------------------------------------------------------------

  DATABASE      MySQL 8.4 (utf8mb4_0900_ai_ci), InnoDB only.
                Chosen to match the course environment (Workbench, Sakila).
                Raw SQL via `mysql2/promise`. NO ORM. Writing the SQL by hand

                Query files live in `server/src/db/queries/` as named,
                parameterized statements. Stored procedures for multi-step
                writes. Views for reporting. Triggers for audit + denormalized
                counters.

  BACKEND       Node.js 20 LTS + Express 4.
                - `express-validator` for request validation
                - `argon2` for password hashing (bcrypt acceptable fallback)
                - `jsonwebtoken` for access tokens + httpOnly refresh cookie
                - `helmet`, `cors`, `express-rate-limit`
                - `pino` for structured logs
                - `vitest` + `supertest` for tests
                - NO business logic in route handlers: routes → controllers →
                  services → repositories (the only layer that writes SQL).

  FRONTEND      React 18 + Vite + TypeScript.
                - `react-router-dom` v6 for routing
                - `@tanstack/react-query` for server state, caching, loading
                  and error states (this is how R8 gets satisfied cheaply)
                - Tailwind CSS for styling + a small hand-rolled component set
                  (Button, Input, Select, Card, Badge, Modal, Toast, Skeleton,
                  EmptyState, ErrorState) — no heavyweight UI kit
                - `zod` for form + response validation, shared with the server
                  via a `shared/` package of types and schemas
                - `vitest` + `@testing-library/react`

  REALTIME      Socket.IO for group chat and live member-count updates.
                Messages are still persisted to MySQL first; the socket only
                broadcasts. If the socket is down, chat degrades to polling.

  TOOLING       Docker Compose (mysql + adminer) so all five machines match.

                GitHub Actions: lint → typecheck → build → test → migrate

SECTION 5 — THE PRODUCT SPEC (NORMATIVE — THIS IS WHAT FAZE IS)
================================================================================

--------------------------------------------------------------------------------
5.1 THE ONE-SENTENCE PITCH
--------------------------------------------------------------------------------
FAZE matches a gamer to a group of other real people who play the same game, on
the same platform, in the same region, at the same hours, with the same reason
for playing — and gets them into a lobby instead of another dead Discord.

--------------------------------------------------------------------------------
5.2 THE PROBLEM (this paragraph goes in the Phase 1 discussion post)
--------------------------------------------------------------------------------
Finding people to play with is still a manual, low-signal process: Reddit LFG
threads, a "looking-for-group" channel in a 4,000-member Discord, or the
game's own random matchmaking, which pairs on skill and nothing else. None of
these model the things that actually determine whether a group sticks together:
time zone and availability overlap, platform, voice-comms preference, whether
someone wants to grind ranked or mess around, language, and age bracket. Those
are relational facts about people, games, and schedules — exactly the kind of
problem a well-normalized database plus a good query answers better than a
chat channel does.

--------------------------------------------------------------------------------
5.3 CORE ENTITIES (the nouns — AGENT 01 turns these into tables)
--------------------------------------------------------------------------------
  user ................ an account
  profile ............. display name, bio, avatar, birth year, primary language
  platform ............ PC, PlayStation, Xbox, Switch, Mobile
  region .............. NA-East, NA-West, EU-West, EU-East, SA, APAC, OCE, ME
  game ................ the catalog (from Kaggle + RAWG/IGDB)
  genre ............... many-to-many with game
  user_platform ....... which platforms a user plays on (M:N)
  user_game ........... which games a user plays, plus rank/hours/goal (M:N)
  playstyle_tag ....... casual, competitive, ranked-grind, completionist,
                        chill-vibes, coach, first-timer, roleplay, speedrun
  user_tag ............ M:N user ↔ playstyle_tag
  availability_slot ... day_of_week + start/end time in the user's tz (1:N)
  group ............... an LFG posting that becomes a persistent group
  group_member ........ M:N user ↔ group, with role + status + joined_at
  group_requirement ... rank floor/ceiling, min age, language, mic required
  join_request ........ a request to join a closed group, with a decision
  message ............. chat in a group
  report .............. a user report (moderation)
  rating .............. post-session teammate rating (1–5 + optional note)
  session ............. a scheduled play session for a group
  etl_run / etl_reject  data pipeline bookkeeping
  audit_log ........... trigger-populated record of sensitive changes

--------------------------------------------------------------------------------
5.4 THE MATCH SCORE (the heart of the app — AGENT 07 implements this in SQL)
--------------------------------------------------------------------------------
Given a searching user U and a candidate open group G, score the pair:

  +40  same game (hard filter — never score across games)
  +15  platform overlap (U plays a platform G requires)
  +12  same region; +6 for an adjacent region
  +15  availability overlap, scaled: (overlapping minutes / 180), capped at 15
  +10  playstyle tag overlap: 5 per shared tag, capped at 10
   +5  language match
   +5  rank inside G's [rank_floor, rank_ceiling] window
   +3  group is not nearly full (breathing room beats a 4/5 scramble)
   +3  recent activity: G had a message or member join in the last 72h
   -20 U fails a hard requirement (min age, mic required, rank window) → G is
       excluded entirely rather than penalized
   -10 U previously left this group or was removed from it

Implemented as a single parameterized SQL query with CTEs and a computed
`match_score` column, ordered DESC, keyset-paginated. NOT computed in
JavaScript over a fetched list. The query is graded — write it in SQL.

--------------------------------------------------------------------------------
5.5 USER JOURNEYS (these are the acceptance-test scripts for the UI agents)
--------------------------------------------------------------------------------
  J1 NEW USER   : sign up → verify → onboarding wizard (pick platforms →
                  search and pick 1–10 games with rank/hours/goal per game →
                  pick region + language → pick playstyle tags → draw weekly
                  availability) → land on a Browse page already ranked for them
  J2 FIND GROUP : Browse → filter by game/platform/region/time → see match
                  score and why ("92% — same region, 2h nightly overlap, both
                  ranked-grind") → open group detail → Join (open) or Request
                  (closed) → land in the group with chat unlocked
  J3 HOST GROUP : Create Group → pick game, platform(s), region, size,
                  requirements, recurring session time → publish → see
                  incoming join requests → approve/deny → group fills
  J4 PLAY       : group dashboard → next session countdown → chat → mark
                  session played → rate teammates
  J5 MODERATE   : report a user → report lands in `report` → an admin view
                  shows open reports and can suspend an account

--------------------------------------------------------------------------------
5.6 EXPLICITLY OUT OF SCOPE (do not build these; say no in the report)
--------------------------------------------------------------------------------
  - Voice chat (Discord already exists; we link out)
  - Real skill/MMR inference from gameplay APIs (self-reported rank only)
  - Payments, premium tiers, ads
  - Native mobile apps (responsive web only)
  - A recommendation ML model (the SQL match score is the feature)

         computed as
         `SUM(GREATEST(0, LEAST(a.end_minute,b.end_minute)
              - GREATEST(a.start_minute,b.start_minute)))`
         grouped by candidate — this is the set-based intersection; do it in
         SQL, not in Node
       - `tag_overlap` — COUNT of shared `playstyle_tag` between the user and
         the group owner (and, stretch goal, the group's modal tag)
       - `region_score` — 12 for equal, 6 when present in `region_adjacency`,
         else 0
       - `activity` — join `v_group_activity`
       - final SELECT computing `match_score` exactly per 5.4, plus a
         `score_breakdown` JSON object built with `JSON_OBJECT(...)` so the UI
         can explain the score ("same region +12, 2h overlap +10")
     Order by `match_score DESC, last_activity_at DESC, group_id DESC` and
     paginate by keyset on that exact tuple.
  2. `GET /api/match?gameId=&platformId=&regionId=&minOpenSlots=&dayOfWeek=
     &afterMinute=&beforeMinute=&tagIds=&limit=&cursor=` — every filter
     optional, all composed into the same query via parameter guards
     (`(:gameId IS NULL OR g.game_id = :gameId)`) so there is exactly one SQL
     statement to maintain and optimize.
  3. `GET /api/match/explain/:groupId` — returns the full breakdown for one
     pair, used by the UI's "why this match" panel and by you for debugging.
  4. Reverse direction: `GET /api/groups/:id/candidates` — for a group owner,
     the ranked list of USERS who fit the group. Same scoring, inverted. This
     doubles the perceived product value and costs one more query.
  5. Degenerate cases must be correct, not crashy:
       - user with zero availability slots → availability component scores 0,
         results still return
       - user with no rank for the game → rank window is not applied as a
         hard filter (do not exclude a beginner for being unranked); note the
         decision in docs/api.md
       - game with zero open groups → return an empty list plus a
         `suggestions` array of the 5 nearest games by genre overlap
  6. Guardrails: `limit` max 50, default 20. A hard cap of 5,000 candidate
     rows scanned per request via the game filter being required OR the
     user's game library being used as the implicit game set.
  7. Write `server/tests/match.test.ts` with a hand-built fixture where you
     KNOW the correct ranking, and assert the exact order and the exact
     scores. This is the one place where a golden-output test is worth it:
     construct 6 groups, compute the expected scores by hand in a comment, and
     assert. If the implementation and the comment disagree, one of them is a
     bug — resolve it, don't relax the test.
  8. Document the query in `docs/matchmaking.md`: the scoring table, the CTE
     walkthrough, the overlap arithmetic with a worked example, and the
     tradeoffs (why not a stored procedure — because the parameter-guarded
     dynamic filters are cleaner as a prepared statement; why not JS — because
     scoring 5,000 candidates in the app layer means fetching 5,000 rows).

SECTION 8 — APPENDIX B: ENGINEERING CONVENTIONS
================================================================================

These are not suggestions. A PR that violates them gets rewritten.

--------------------------------------------------------------------------------
B.1 SQL CONVENTIONS
--------------------------------------------------------------------------------
  - Table names: singular, snake_case (`user`, `lfg_group`, `group_member`).
    Join tables are `<a>_<b>` with a composite primary key.
  - Primary keys: `<table>_id`. Surrogate auto-increment keys everywhere except
    pure join tables, which use the composite natural key.
  - Foreign keys: named `fk_<child>_<parent>`, with an EXPLICIT
    `ON DELETE`/`ON UPDATE` rule chosen per relationship and justified in
    docs/schema.md. Never rely on the default.
  - Indexes: named `idx_<table>_<cols>`; uniques `uq_<table>_<cols>`;
    fulltext `ft_<table>_<col>`. Every index carries a SQL comment naming the
    query it exists for. An index nobody can name a query for gets deleted.
  - Booleans: `BOOLEAN NOT NULL DEFAULT 0` (TINYINT(1) under the hood), named
    affirmatively (`mic_required`, not `no_mic`).
  - Enums for small closed sets that the application branches on; lookup
    tables for sets that grow or carry attributes (region, platform, genre,
    playstyle_tag are tables, not enums — they have names, slugs and, in
    region's case, an adjacency relation).
  - Timestamps: `DATETIME` in UTC, never `TIMESTAMP` (2038 and implicit
    timezone conversion), except `message.created_at DATETIME(3)` where
    ordering needs millisecond precision. The pool is configured
    `timezone:'Z'` so nothing is reinterpreted on the way in or out.
  - Money: none in this project. If that ever changes, `DECIMAL`, never FLOAT.
  - Keyword case: SQL keywords UPPERCASE, identifiers lowercase.
  - Every `.sql` query file opens with a comment block: what it answers, its
    parameters, the indexes it relies on, and its expected row count order of
    magnitude.
  - NULL means "unknown," never "zero" and never "false." If a column can't
    be unknown, make it NOT NULL.
  - No `SELECT *` in application queries. Name the columns, so adding a column
    never changes a response shape.
  - No business logic in the ORM layer, because there is no ORM. Repositories
    hold SQL; services hold rules.

--------------------------------------------------------------------------------
B.2 BACKEND CONVENTIONS
--------------------------------------------------------------------------------
  - Layering is absolute: routes → controllers → services → repositories.
    SQL appears in exactly one layer. A route file that imports the pool is a
    defect.
  - Every multi-table write uses `withTransaction` or a stored procedure. No
    exceptions (R9).
  - Every route validates its input with a shared zod schema before the
    controller runs. Unvalidated `req.body` access is a defect.
  - Errors: throw typed `AppError(code, httpStatus, message, field?)`. Never
    `res.status(500).json({error: e.message})` — that leaks internals.
  - Logging: pino, structured, with the request id. No `console.log` in
    committed server code. Never log a password, token, cookie or full row of
    user data.
  - Async: no floating promises. Every `await` is either awaited or
    deliberately `void`ed with a comment.
  - Configuration: read env once at boot into a validated config object (zod
    again); `process.env` never appears below the config module, so a missing
    variable fails at startup rather than at 2am in a request.
  - Time: the server computes in UTC. Conversion to local time happens in
    `shared/` (so client and server agree) and is displayed by the client.

--------------------------------------------------------------------------------
B.3 FRONTEND CONVENTIONS
--------------------------------------------------------------------------------
  - Feature-folder structure: `client/src/features/<feature>/{components,
    hooks,api,types}`. A feature NEVER imports from another feature — shared
    things move to `components/ui`, `lib`, or `@faze/shared`.
  - Server state lives in React Query, keyed through the `queryKeys` factory.
    Local UI state lives in `useState`. There is no global store; if you reach
    for one, the data probably belongs in React Query.
  - Every async surface renders four states (R8). The reviewer's first
    question on any PR with a fetch is "show me the empty and error states."
  - No hardcoded colors, spacing or font sizes in feature code — tokens only.
  - No `any`. No `@ts-ignore` without a comment naming the upstream issue.
  - Forms: zod schema + field-level errors + a disabled/loading submit. Server
    field errors map onto inputs by the `field` in the error envelope.
  - Accessibility: keyboard reachable, visible focus, labeled controls,
    contrast ≥ 4.5:1. axe clean before merge.
  - Dates and times are rendered in the viewer's timezone with the zone shown
    wherever ambiguity would cost someone a session.

--------------------------------------------------------------------------------
B.4 GIT AND REVIEW CONVENTIONS
--------------------------------------------------------------------------------
  - Branches: `agent/agent-NN-<short-name>` for agent work,
    `fix/<short-name>` for follow-ups, `docs/<short-name>` for doc-only.
  - Commits: `agent-NN-vX: <imperative summary>` for agent work; otherwise
    conventional prefixes (`fix:`, `docs:`, `chore:`, `perf:`, `test:`).
  - One PR per agent. PR description follows the template: agent number,
    what changed, evidence per criterion, ⛔ items.
  - Bryan is a required reviewer. A second teammate reviews anything touching
    their lane.
  - Never force-push `main`. Never merge red CI. Never merge your own PR
    without at least one approval, with one exception: a build-breaking
    hotfix, which must be announced in Discord and reviewed after the fact.
  - Rebase your branch on main before merging; squash-merge to keep main
    readable as one commit per agent.

--------------------------------------------------------------------------------
B.5 DOCUMENTATION CONVENTIONS
--------------------------------------------------------------------------------
  Every doc in `/docs` has one owner and one purpose:
    schema.md ......... the data dictionary + normalization argument (Česko²)
    api.md ............ the frozen API contract (Bryan)
    data.md ........... sources, licenses, ETL mapping, quality (Arman)

SECTION 9 — APPENDIX C: ANTI-PATTERNS (things that will get a PR rejected)
================================================================================

C1.  Computing the match score in JavaScript. The whole point of the project
     is that this is a query. If you fetch rows and sort them in Node, you
     have built a worse product AND thrown away the graded work.
C2.  An ORM or a query builder smuggled in "just for this one table." Raw
     parameterized SQL, everywhere, consistently.
C3.  Application code writing `lfg_group.member_count`. Triggers own it. If
     you need it to change, change what the trigger watches.
C4.  Capacity checks without a row lock. `SELECT count → if (count < max) →
     INSERT` is a race condition, not a check. Lock or lose a slot.
C5.  `OFFSET` pagination on any table that will grow. Keyset only.
C6.  A list endpoint without a `limit` cap. One client bug becomes a full
     table scan into JSON.
C7.  `SELECT *` in application code, and returning a raw DB row as an API
     response. Every response shape is explicit and reviewed.
C8.  Fake data in a code path. Mock game titles, a hardcoded user id, a
     placeholder avatar array. Fixtures live in tests and seeds. If the
     database is empty, the UI shows an EmptyState — it does not invent rows.
C9.  A screen with only a happy path. Loading, empty, error, loaded — all four.
C10. Swallowing an error. `catch (e) {}` and `catch (e) { console.log(e) }`
     both hide the bug that will cost an hour later. Handle it or rethrow it.
C11. Timezone math done ad hoc in a component. One conversion function, in
     `shared/`, with tests, used everywhere.
C12. `String` concatenation into SQL — including into ORDER BY and LIMIT.
     Allow-list identifiers; parameterize values.
C13. A migration edited after it was applied. Write a corrective migration.
     The checksum guard will catch you, and it should.
C14. Secrets in git, in a comment, in a test fixture, or in a log line.
C15. A PR that says "works" with no evidence. Evidence or it did not happen.
C16. Marking an agent ✅ with an empty Appendix A block.
C17. Doing another person's lane without telling them. Lanes exist so four
     people can move at once; stepping on one costs more than it saves. Post
     in Discord first.
C18. Building anything on the out-of-scope list in 5.6 because it seemed fun.
     Scope discipline is a graded behavior in a semester project.
C19. Deferring the ER diagram and the report to the last week. AGENT 18 exists
     in the middle of the document on purpose.
C20. Letting `main` stay red. A red main blocks four other people.

D.3 USEFUL DIAGNOSTIC SQL
--------------------------------------------------------------------------------
  -- schema overview
  SELECT table_name, engine, table_rows, table_collation
    FROM information_schema.tables WHERE table_schema='faze' ORDER BY 1;

  -- every foreign key and its delete rule
  SELECT rc.constraint_name, rc.table_name, rc.referenced_table_name,
         rc.delete_rule, rc.update_rule
    FROM information_schema.referential_constraints rc
   WHERE rc.constraint_schema='faze' ORDER BY 2,1;

  -- every check constraint
  SELECT constraint_name, check_clause
    FROM information_schema.check_constraints WHERE constraint_schema='faze';

  -- every index
  SELECT table_name, index_name, GROUP_CONCAT(column_name ORDER BY seq_in_index)
    FROM information_schema.statistics WHERE table_schema='faze'
   GROUP BY 1,2 ORDER BY 1,2;

  -- denormalization honesty check (must return zero rows)
  SELECT * FROM v_member_count_reconciliation WHERE drift <> 0;

  -- data health
  SELECT 'users' t, COUNT(*) n FROM user
  UNION ALL SELECT 'games', COUNT(*) FROM game
  UNION ALL SELECT 'groups', COUNT(*) FROM lfg_group
  UNION ALL SELECT 'members', COUNT(*) FROM group_member
  UNION ALL SELECT 'messages', COUNT(*) FROM message
  UNION ALL SELECT 'slots', COUNT(*) FROM availability_slot;

  -- etl audit
  SELECT * FROM etl_run ORDER BY run_id DESC LIMIT 10;
  SELECT reason, COUNT(*) FROM etl_reject GROUP BY reason ORDER BY 2 DESC;

  -- what the optimizer actually did
  EXPLAIN FORMAT=JSON <the query>;
  SELECT * FROM sys.schema_unused_indexes;
